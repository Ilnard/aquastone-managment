# Aquastone Management

Локальная разработка сайта управления процессами производства.

## Подключение PostgreSQL

1. Убедитесь, что локальная служба PostgreSQL запущена.
2. Откройте `.env` и укажите пароль роли `postgres` в `PGPASSWORD`. Если база создана под другим именем или пользователем, поменяйте `PGDATABASE` или `PGUSER`.
3. Запустите проект командой `npm run dev`.

При запуске API создаёт таблицы (`processes`, `process_attachments`, `process_history`, `process_comments`, `employees`, `sessions`, `catalog_items`, `decor_glues`, `furniture_companies`, `furniture_makers`) и убирает устаревшее: неиспользуемые столбцы и ключи данных процессов из старых версий. Номер процесса хранится как уникальный ключ, остальные поля — как JSONB, чтобы добавлять поля процесса без миграции на каждый новый атрибут. Интерфейс показывает статус подключения в верхней панели.

## Демо-данные

`npm run seed` — **удаляет все процессы** (с историей, комментариями и файлами) и создаёт 36 новых случайных на всех этапах и статусах: с командой, замером и чертежом, клеем из «Клея по декорам», мебельщиками из справочника, монтажниками, фотоотчётом, комментариями и историей. Перед удалением спрашивает подтверждение.

- `npm run seed -- --yes` — без вопроса;
- `npm run seed -- --count 50` — другое количество (1–300).

Сотрудники и справочники не удаляются. Если для какой-то роли нет сотрудника или в «Мебельщиках» нет ни одного мебельщика, скрипт добавит демо-записи (демо-сотрудники без доступа на сайт).

Откройте адрес Vite, который появится в терминале. API работает на `http://127.0.0.1:3001`, а `/api` в dev-среде проксируется к нему.

## Вход и сотрудники

- При первом запуске сервер создаёт учётную запись директора и печатает её логин и пароль в консоль (окно, где запущен `npm run dev`). Войдите и смените пароль в «Личном кабинете».
- Регистрирует и удаляет сотрудников только директор: логин придумывается из имени, пароль — случайный; они показываются директору один раз.
- Сотрудник может сменить логин и пароль в «Личном кабинете» (кнопка с именем внизу слева или аватар справа вверху).
- Потерян пароль: `npm run reset-password -- <логин или имя>` — печатает новый пароль. Без параметров показывает список логинов.
- Пароли хранятся только в виде хэша (scrypt), вход — через cookie-сессию на 30 дней. Для работы по HTTPS задайте в `.env` `COOKIE_SECURE=1`.
- Активность сотрудника (все его изменения процессов «было → стало») — на его странице в разделе «Сотрудники»; видят директор и менеджер.

## API

- `GET /api/health` — статус подключения к базе.
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` — вход, выход, кто вошёл.
- `PUT /api/auth/password`, `PUT /api/auth/login` — смена своего пароля или логина (нужен текущий пароль).
- `GET /api/employees` — список активных сотрудников.
- `POST /api/employees` — добавить сотрудника: имя и список ролей (`{ name, roles: ['Технолог', 'Монтажник'] }`).
- `PUT /api/employees/:id` — изменить роли или имя сотрудника; при переименовании назначения в процессах переходят на новое имя.
- `POST /api/employees/:id/credentials` — новый пароль сотруднику (директор).
- `GET /api/employees/:id/activity` — активность сотрудника (директор, менеджер).
- `DELETE /api/employees/:id` — удалить сотрудника (директор).

Все запросы, кроме `/api/health` и входа, требуют входа на сайт.
- `GET /api/processes` — список процессов.
- `POST /api/processes` — создать процесс; номер обязателен и должен быть уникальным.
- `PATCH /api/processes/:id` — сохранить изменения процесса: `{ changes: { поле: значение }, baseVersion }`. Меняются только присланные поля. Если после `baseVersion` кто-то уже изменил те же поля, сервер отвечает `409` с актуальным процессом — правки коллег не затираются. Изменения в разных полях объединяются без конфликта.
- `PUT /api/processes/:id` — устарел: отвечает `409` с просьбой обновить страницу (старые открытые вкладки не перезапишут процесс целиком).
- `GET /api/processes/:id/history` — история создания и изменения процесса.
- `GET /api/processes/:id/attachments` — список вложений.
- `POST /api/processes/:id/attachments` — загрузить фото, PDF, DWG или DXF до 50 МБ.
- `GET /api/processes/:id/attachments/:attachmentId` — скачать вложение.
- `DELETE /api/processes/:id/attachments/:attachmentId` — удалить вложение.
- `GET /api/processes/:id/comments`, `POST /api/processes/:id/comments` (`{ body }`) — комментарии к процессу.
- `DELETE /api/processes/:id/comments/:commentId` — удалить комментарий (автор или директор).
- `GET /api/decor-glues` — справочник «Клей по декорам» (видят все сотрудники).
- `POST /api/decor-glues`, `PUT /api/decor-glues/:id`, `DELETE /api/decor-glues/:id` — добавить, изменить, удалить позицию (менеджер, директор). Поля: `material`, `brand`, `decor`, `mainGlue`, `altGlue`, `note`. Декор уникален внутри пары «материал + бренд».

При первом запуске таблица `decor_glues` заполняется стартовыми позициями из `src/decorGlues.js` (по 5 декоров: кварц Avant, кварц Grandex, акрил Neonarm, акрил Grandex), а их клеи добавляются в справочник «Клеи».
- `GET /api/notifications` — уведомления сотрудника: изменения и комментарии коллег по процессам, где он назначен (директору — ещё новые процессы и смена этапов по всем), за 2 недели; напоминания: монтаж сегодня и завтра, просроченный срок производства. `POST /api/notifications/read` — отметить прочитанным.
- `GET /api/furniture` — справочник «Мебельщики»: `[{ id, name, makers: [{ id, name, phone }] }]` (видят все).
- `POST /api/furniture`, `PUT /api/furniture/:id` (`{ name, makers: [{ name, phone }] }` — список мебельщиков заменяется целиком), `DELETE /api/furniture/:id` — менеджер, директор. Телефоны приводятся к виду `+7 (999) 888-77-66`.

В процессе поля `furnitureCompany`, `furnitureMaker`, `furnitureMakerPhone`: компания и мебельщик выбираются из справочника или вводятся вручную. При первом запуске телефон с подписью «Мебельщик» из «Телефонов контактов» переносится в `furnitureMakerPhone`, а справочник заполняется компаниями и мебельщиками из существующих процессов (телефон — из последнего изменённого процесса).

## Заявки из конструктора

Конструктор столешниц (проект `aquastone-constructor`) отправляет расчёт кнопкой **«Отправить заявку на рассмотрение»**. Заявки собираются в разделе **«Заявки»** — его видят только **директор и менеджер** (у остальных ролей пункта в меню нет, а сервер отвечает `403`).

- Клиент указывает ФИО и телефон. Менеджер или директор, вошедший на этот сайт в том же браузере, отправляет без формы — заявка сохраняется от его имени.
- Статусы: **Новая → В работе → Создан процесс**, или **Отклонена** (можно вернуть в работу). Новые заявки — счётчик в меню и уведомление в колокольчике.
- В карточке заявки — эскиз из конструктора, размеры деталей и вырезов, комплект листов, выход материала, стыки, ориентир по стоимости и комментарий менеджера.
- «Создать процесс» открывает форму нового процесса с клиентом, телефоном, материалом и декором из заявки. После создания заявка привязывается к процессу, а в процесс добавляется комментарий с расчётом.

API:
- `POST /api/requests` — новая заявка (без входа): `{ project, contact: { name, phone }, website }`. `website` — скрытое поле-ловушка для ботов. С одного адреса — не больше 5 клиентских заявок за 10 минут. Если запрос пришёл с сессией менеджера или директора, `contact` не нужен.
- `GET /api/requests` — список заявок (менеджер, директор).
- `PATCH /api/requests/:id` — `{ status?, note?, processNumber? }` (менеджер, директор).

Конструктор должен обращаться к этому серверу по тому же адресу `/api`: при разработке его Vite проксирует `/api` на `MANAGEMENT_API_URL` (по умолчанию `http://127.0.0.1:3001`). На сервере настройте так же — через nginx на том же домене, например `/api` → этот сервер. Тогда менеджер, вошедший в систему управления, будет узнан и в конструкторе.

## Изделия процесса

Один процесс может состоять из нескольких изделий из разных материалов — например, столешница для кухни из кварца и столешница в санузел из акрила. У каждого изделия свои **изделие, материал, декор и клей** (поле `items` в данных процесса).

- **Создание и правка** — в форме «Создать процесс» и в карточке «Информация о заказе» → «Изменить»: кнопка «Добавить изделие», корзина — убрать. Декор можно выбрать из подсказок справочника «Клей по декорам» — основной клей подставится сам.
- **Клей** выбирается для каждого изделия из кварца или акрила. На вкладке «Производство» ЧПУ и обработчик подбирают клей по изделиям, но не могут менять сами изделия — это проверяет и сервер.
- **Список процессов** показывает материалы и декоры всех изделий (два первых и «+ ещё N»), фильтр «Материал» находит процесс по любому изделию, поиск — по изделию, материалу, декору и клею. В выгрузке CSV изделия перечислены через «; ».
- **Старые процессы** при запуске сервера переводятся автоматически: прежние «изделие / материал / декор / клей» становятся изделием №1.

## Статистика «Произведено за месяц»

В разделе «Обзор» внизу — статистика по месяцам: сколько изделий из **акрила**, **кварца**, **HPL компакта** и **всего** произведено, и список процессов этого месяца (клик открывает процесс, «Скачать CSV» — выгрузка списка).

- В месяц попадают процессы, **завершённые** в этом месяце. Дата создания не важна: процесс, созданный в сентябре и завершённый в октябре, считается в октябре.
- Дату завершения (`completedAt`) ставит сервер, когда этап меняют на «Завершён»; если процесс вернули в работу, дата убирается. Вручную её не прислать. Для процессов, завершённых раньше, дата при запуске сервера берётся из истории.
- Месяц переключается стрелками или списком и хранится в адресе: `/overview?month=2026-10`.

## Интерфейс списка и навигация

- **Быстрый поиск** — `Ctrl+K` (на Mac `⌘K`) или поле в шапке: процессы по номеру, клиенту, последним цифрам телефона, адресу, декору; разделы сайта.
- **Уведомления** — колокольчик в шапке, обновляется раз в 30 секунд; открытие панели отмечает всё прочитанным.
- **Адреса страниц** (React Router): у каждого раздела свой адрес — `/processes`, `/processes/1702` (процесс), `/overview`, `/calendar`, `/requests`, `/requests/12` (заявка), `/employees`, `/catalogs`, `/account`. После обновления страницы открыт тот же раздел, кнопки «назад/вперёд» браузера работают, ссылкой можно поделиться («Действия → Скопировать ссылку» на странице процесса). Старые ссылки с `#/process/…` открываются по-новому автоматически.
- **Список процессов** — фильтры (менеджер, материал, только мои, скрыть завершённые), настройка колонок (запоминаются в браузере), выбор строк галочками и экспорт выбранных, по 25 процессов на странице. «Следующая дата» — ближайший монтаж или срок производства (просроченный — красным).

## Этапы и статусы

Этапы по порядку: **Новый заказ → Замер → Проектирование → Фрезеровка/Распил → Шлифовка/Полировка/Монтаж мойки → Произведено → Монтаж → Завершён**. У рабочих этапов (Замер, Проектирование, Фрезеровка/Распил, Шлифовка…, Монтаж) есть статус `stageStatus`: «Не готов» / «Готов».

| Шаг | Кто | Что происходит |
|---|---|---|
| Новый заказ → Замер · Не готов | Менеджер | «Передать на замер» — когда данные собраны и получена предоплата/оплата |
| Замер · Готов | Замерщик | дата замера ставится сегодняшняя, если не указана |
| → Проектирование · Не готов | Технолог | «Взять в работу» — технолог назначается на процесс |
| Проектирование · Готов | Технолог (назначенный) | |
| → Фрезеровка/Распил · Не готов | ЧПУ | «Взять в работу» |
| Фрезеровка/Распил · Готов | ЧПУ (назначенный) | |
| → Шлифовка/Полировка/Монтаж мойки · Не готов | Обработчик | «Взять в работу» |
| «Готово» → Произведено | Обработчик (назначенный) | статус не нужен — процесс сразу «Произведено» |
| → Монтаж · Не готов | Бригадир монтажников | «Перевести в монтаж», назначает монтажников (несколько) |
| Монтаж · Готов | Бригадир или назначенные монтажники | нужен минимум 1 фото в «Фотоотчёте» |
| → Завершён | Менеджер | «Закрыть процесс» |

Пока следующий не забрал процесс, исполнитель может вернуть «Не готов». Менеджер и директор могут поставить любой этап вручную («Действия → Изменить этап вручную»). «Нужны данные» — отметка `needsData` (+ `needsDataNote`), её ставит любой сотрудник на любом этапе. Переходы проверяет сервер (`src/permissions.js` — общие правила для сервера и интерфейса). При первом запуске старые этапы переносятся: «Ожидает замера» → Замер · Не готов, «Замер проведён» → Замер · Готов, «Производство» → Фрезеровка/Распил · Не готов, «Готов к монтажу» → Произведено, «Нужны данные» → Новый заказ + отметка; монтажники становятся списком.

В колокольчике — очередь: процессы, которые сотрудник может взять в работу по своей роли, и готовые к закрытию у менеджера.

## Права по ролям

- Директор и менеджер меняют всё. Раздел «Заявки» видят только они.
- Вкладки: «Замер» — замерщик и технолог; «Проектирование» — технолог; «Производство» — ЧПУ и обработчик; «Монтаж» (даты, фотоотчёт) — монтажники и бригадир.
- Команду процесса меняет менеджер; монтажников назначает и бригадир.
- Карточку «Сроки» и отметку «Нужны данные» может менять любой сотрудник.
- Файлы загружает и удаляет тот, кто может менять соответствующую вкладку. Последнее фото фотоотчёта при «Монтаж · Готов» удалить нельзя.

## GitHub Pages

Для публикации используйте `npm run deploy -- "Сообщение коммита"` из ветки `main`. Команда создаёт коммит с этим сообщением в `main`, собирает статическую демо-версию и создаёт коммит с тем же сообщением в `deploy`, затем отправляет обе ветки в GitHub. Если сообщение не указано, команда запросит его в терминале. Для GitHub Pages в настройках репозитория выберите **Settings → Pages → Deploy from a branch → deploy → /(root)**.

GitHub Pages раздаёт только статические файлы: PostgreSQL API и загрузка вложений там не работают. В Pages интерфейс использует браузерное хранилище; общая многопользовательская версия должна размещаться на хостинге, который запускает Express API, и иметь доступ к PostgreSQL и постоянному файловому хранилищу.

API слушает только `127.0.0.1`. Перед публикацией в интернете включите HTTPS (и `COOKIE_SECURE=1`), а сервер API запускайте за обратным прокси.

Адреса без `#` требуют, чтобы веб-сервер на любой путь сайта отдавал `index.html` (React Router сам откроет нужный раздел). `npm run dev` и `npm run preview` так уже делают; `npm run deploy` кладёт копию `index.html` в `404.html` для GitHub Pages. Для nginx:

```nginx
location / {
  root /var/www/aquastone/dist;
  try_files $uri /index.html;
}
location /api/ { proxy_pass http://127.0.0.1:3001; }
```
